# PR #127: Keep the popup's dropdowns on screen, and let the item picker search without a form — Zai review

**URL**: https://github.com/BeamLabEU/phoenix_kit_catalogue/pull/127
**Reviewer**: Zai (GLM-5.3), no tools; answered from a brief carrying the full `lib/` diff and the modal's render
**Date**: 2026-09-17
**Scope**: the popover change at `d0a6b0d`

### Checked and sound

- **A, anchor plumbing:** `popover_anchor/1` yields a valid unique ident per DOM id; `--anchor-h: span-left` is daisyUI 5's own `.dropdown-end` recipe, so right-alignment is preserved; `max-height: calc(50dvh - 2.5rem)` + `flip-block` guarantees one side fits a toolbar-top button (there is always ≥ half the viewport below it).
- **A, stays open across re-renders:** a column toggle patches only `<li>`/button attrs; the `<ul>` is id-stable and never removed, and `:popover-open` is UA state on the element — LiveView's morph keeps it open. Auto `popover` supplies outside-click and Escape close, as the doc now claims.
- **B, render-then-show ordering:** `popover="manual"` is `display:none` until shown, so the server-rendered ul doesn't flash in flow; `updated()` → `syncListbox()` shows each newly rendered ul; the `matches(":popover-open")` guard avoids re-show churn on option-only patches.
- **B, clipping:** the top layer escapes the modal-box, host panels and any `overflow` ancestor; the ul is a DOM child of the `phx-click-away` wrapper, so clicks on options don't trip click-away; `width: anchor-size(width)` + `flip-block` is the right combobox geometry, and the cap keeps one side always viable.
- **B, no-anchor fallback:** JS overrides the UA open-popover styles (`inset/margin`) inline *after* `showPopover()`; browsers without the popover API ignore the attribute entirely so the element is placeable via `position:fixed` pre-paint; scroll-capture + resize re-place; cleanup in `destroyed()` is balanced (removing undefined handlers is a no-op).
- **C, IME and delegation:** skipping `input` while `isComposing` and queueing on `compositionend` is correct in both event orders (either order re-queues the same value into the same pending timer — one send, not two). `stopPropagation` on `input`/`change` keeps the events away from LiveView's delegated form `phx-change` (the host-shim path becomes inert, so there is exactly one sender — no duplicate search).
- **C, routing:** `pushEventTo(this.el, …)` matches the colocated `.AutoLoad` pattern — **provided the wrapper div itself carries `phx-target={@myself}`**; the input's own `phx-target` does not cover `this.el`. Verify the wrapper attr (likely present, since `phx-click-away`'s "close" needs it).

### Findings

1. **(B, unsure — test this one) `syncListbox`/`phx-click-away`:** in engines where a manual popover's `::backdrop` is hit-testable, a click anywhere outside the listbox while it is open lands on the backdrop and is swallowed — and if backdrop events retarget to the originating `<ul>`, the target is *inside* the wrapper, so `phx-click-away` never fires: **picker stuck open and the page unclickable until Escape**. One-line repro: open the picker, click an unrelated page button. Fix if it reproduces: `[popover]::backdrop { pointer-events: none }` scoped to the listbox.
2. **`column_toggle` (A), short screen + modal-box scroll:** the popover has no `position-visibility: anchors-visible` (B got it, A didn't). If the modal-box itself scrolls (short viewport) while the menu is open, the button scrolls out under the box's top edge and the fixed popover keeps tracking the clipped anchor — a menu floating with no visible trigger, closable only by light dismiss. Add `position-visibility: anchors-visible` to the ul for symmetry.
3. **ItemSelectorModal header row (Q3), narrow screen:** `div.flex.items-center.gap-2` holding search + root-mode join + column toggle + view toggle has **no `flex-wrap`**; on a narrow viewport (worse when the root switcher renders three more buttons) the rightmost buttons overflow and are clipped by the modal-box's horizontal overflow — Columns/View literally unclickable. Add `flex-wrap`.
4. **`queueQuery`/`destroyed` (C):** `clearTimeout(this._queryTimer)` on destroy silently drops the last <300 ms of typing. If a host re-renders its rows mid-debounce (the stale-client-echo class of patch, which this codebase has hit before), the keystrokes never reach the server — a lost search with no error. Flush (`pushEventTo` immediately) instead of clearing when a query is pending.
5. **`placeListbox` (B fallback), neither side fits:** `height <= below || below >= above` places *below* even when `height > below` (e.g. below=200, above=100, height=300) → bottom cut off; only `top` is clamped ≥0, the bottom isn't. Clamp so the menu's bottom stays at `innerHeight`, or pick the roomier side.
6. **`popover_anchor/1` (minor):** ids differing only in non-ident characters (`a.b` vs `a-b`) collapse to the same anchor name, and anchor names are document-global — the second popover then anchors to the first's trigger and renders in the wrong place. Fine as long as DOM ids are unique and don't collide after sanitization.
7. **(A, unsure, minor) no-anchor browsers:** daisyUI's `@supports not (position-area: bottom)` branch centers the menu in the *viewport* (`margin:auto`), not at the button — visible and clickable but far from its trigger; B has a JS fallback, A deliberately doesn't. Acceptable, but worth knowing Firefox/Safari users see a centered menu.

**Q4, ranked:** #3 (toolbar overflow) is the only *new* unreachable-control path in the modal render — it's the same bug class the client reported, rotated 90°, and it ships in this diff's surface. Then #1 (stuck-open backdrop), then #2/#4. Nothing else in the modal render sticks out: the 48vh list + 26vh tray scroll independently inside a scrolling modal-box, the nested detail dialog stacks correctly above the selector (and light-dismisses any open Columns popover on the opening click), and the tray/action row stay reachable via the box's own scroll on short screens. One non-dropdown nit while you're in the file: the `.ScrollTop` hook's `updated()` assigns `this.key` twice back-to-back — harmless, but the duplicated line suggests an edit was half-applied there.
